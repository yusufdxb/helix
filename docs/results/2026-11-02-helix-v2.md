## C1: content-fault detection, held-out (detected within 2 s of onset / episodes)

Faults are injected into `/utlidar/imu` across 3 held-out recordings, with 40 episodes per class. HELIX means the deployed
`go2.cfg`: rate, frozen, stamp and residual checks. It has no range check.

| Class | B-rate | B-range | union | **HELIX** | frozen | stamp | residual | oracle | sham |
|---|---|---|---|---|---|---|---|---|---|
| F1 dropout | 40 | 0 | 40 | **40** | 0 | 0 | 0 | 0 | 0 |
| F2 rate collapse | 40 | 4 | 40 | **40** | 0 | 0 | 0 | 0 | 0 |
| F3a frozen payload and stamp | 0 | 0 | 0 | **40** | 40 | 40 | 20 | 21 | 0 |
| F3b frozen payload, live stamp | 0 | 0 | 0 | **40** | 40 | 0 | 20 | 21 | 0 |
| F4 gyro z bias 0.2 rad/s | 0 | 4 | 4 | **40** | 0 | 0 | 40 | 40 | 0 |
| F4 gyro z bias 0.1 rad/s | 0 | 4 | 4 | **4** | 0 | 0 | 4 | 40 | 0 |
| F5 gyro scale ×0.5 | 0 | 3 | 3 | **7** | 0 | 0 | 7 | 11 | 0 |
| F6 gyro z sign flip | 0 | 6 | 6 | **11** | 0 | 0 | 11 | 18 | 0 |
| F7 gyro noise σ 0.3 | 0 | 5 | 5 | **0** | 0 | 0 | 0 | 23 | 0 |
| bias 1.0 (positive control) | 0 | 6 | 6 | **40** | 0 | 0 | 40 | 40 | 0 |

Median HELIX latency: F1 25 ms, F3 49 ms, F4(0.2) 0.28 s, F5 0.50 s, F6 0.56 s.

The oracle and sham columns cover only the residual check family; the rate and frozen checks are not part of them.

What this shows:
- **Frozen and stuck streams.** The rate and range baselines miss them completely (0/80), and HELIX catches all 80. This is the most clearly useful result: a republished stale buffer keeps its rate and stays in range.
- **Cross-sensor gyro residual.** The residual between body IMU and LiDAR IMU catches a 0.2 rad/s bias in 40/40 episodes. At 0.1 rad/s, or for scale and sign faults during mostly-standing data, it catches few: the deployed threshold (0.105) is conservative. The oracle (threshold 0.064, still within 2 FA/h) shows the same check family can reach 40/40 at 0.1 rad/s. On F7 noise HELIX is **worse** than the union (0 vs 5), because B-range catches spikes and HELIX dropped the range check.
- **Sham.** Shifting the LiDAR stream by 20 s, with identical calibration, gives 0 detections in every class. Detection therefore depends on alignment between the two sensors, not on the check firing at random.

## C2: stop verification, held-out (36 walk-to-StopMove events)

| Variant | HELIX StopVerifier | B-est (estimator speed) | B-ack (command acknowledged) |
|---|---|---|---|
| genuine stop | VERIFIED 36 | VERIFIED 36 | VERIFIED 36 |
| estimator lies (velocity zeroed, robot still walking) | **FAILED 35, VERIFIED 1** | VERIFIED 36 | VERIFIED 36 |
| non-compliance splice (positive control) | FAILED 35, VERIFIED 1 | UNVERIFIED 35, VERIFIED 1 | VERIFIED 36 |
| sham (raw groups replaced by standing data) | VERIFIED 36 | VERIFIED 36 | VERIFIED 36 |
| native stop bags, no `/lowstate` (4 events) | UNVERIFIED 4 | VERIFIED 4 | VERIFIED 4 |

- **The estimator-lies case.** This is the case the design targets. A checker that trusts the estimator's velocity reports "stopped" every time (36/36). HELIX needs a quiet raw-sensor group (joint dq or IMU) and no group still moving, so it refuses 35/36.
- **The sham.** It is fooled, as it must be: HELIX is only as independent as its raw sensors.
- **Missing evidence.** When `/lowstate` is absent, HELIX says UNVERIFIED rather than VERIFIED. That is the intended behaviour: it does not claim a stop it cannot see.
- **The one wrong VERIFIED.** It is the same event in both lies and splice: partialwalk1, event 12, at 460.2 s. The pre-stop segment spliced in after the stop was already nearly still. Estimator metric 0.93 against quiet 1.0, joints 0.18 against 0.23. The robot was probably not walking when that StopMove arrived, so HELIX found no motion evidence to refuse on.

## Live ROS 2 node smoke test (`eval/node_smoke.sh`)

The C++ node (`helix_monitor_node`) was run against real bag playback with `ros2 bag play`. Real time, Cyclone DDS.

| Case | Input | Result |
|---|---|---|
| clean | odin-hw-standing-20260901-1935 (79 s; `/utlidar/imu`, `/sportmodestate`, `/lowstate`) | no alarm during playback. 3 rate alarms at +81.5 s, when the bag ended |
| stop | native stop bag 20261017T222205 (`/sportmodestate`, StopMove requests remapped to a private topic) | 53 StopMove requests seen, 1 verdict: UNVERIFIED after 2.01 s (no `/lowstate`, as expected) |
| frozen positive control | constant `/sportmodestate` from `ros2 topic pub` at 300 Hz | frozen, stamp and rate raised on `sport` |

**Interoperability finding.** The GO2 publishes `SportModeState` samples of 516 bytes, but the `unitree_go`
message type serializes to 236 bytes. The firmware type appears to carry extra trailing fields. Cyclone DDS
accepts the samples and ignores the tail. Fast DDS, the Humble default, drops them silently during replay, so a
monitor would see no `/sportmodestate` at all. The node therefore warns when the RMW is not
`rmw_cyclonedds_cpp`, and again when any monitored stream is silent for 5 s.

## Deviations from the registration

1. Calibration factors were fixed in code before the freeze but not spelled out in the registration:
   - rate band 0.8× DEV min to 1.2× DEV max rate;
   - timeout max(3 periods, 1.5× DEV max gap);
   - frozen and stall windows max(0.05 s, 1.5× DEV max);
   - residual threshold 1.5× DEV max held residual;
   - stop-group quiet 1.5× DEV post-stop p95, moving 0.5× DEV pre-stop p5, with the geometric mean used where the two overlap.
2. The inertial evidence group uses only the body gyro (`/lowstate` imu gyro xyz). The registration listed gyro and accel.
3. Native single-source stops: all 5 tracked native bags were scored. 4 contain a Move (1008) followed by StopMove (1003), the harness's stop definition. That matches the registered count of 4.
4. Two harness fixes landed before the freeze: one flushes alarms at the end of a replay, the other parses the B-z config repr correctly. They change no HELIX logic.
5. For the splice positive control, the registration said B-est must FAIL. B-est has no moving threshold, so it can only return VERIFIED or UNVERIFIED. The control was scored as "B-est not VERIFIED" (35/36).
6. The offline harness counts a stop only when a StopMove follows a Move. The live node verifies every StopMove (api 1003), and a repeated StopMove restarts the verification, so a burst gives one verdict.
7. The live node requires the Cyclone RMW (see above).

## Limits (what is not shown)

- **No external ground truth.** Nothing like motion capture backs the stop study. Genuine stops assume the GO2 complied with each StopMove in the protocol's "still" segments.
- **Injected faults only.** All faults are synthetic, injected at the message level into recorded data. No naturally occurring sensor fault is in the held-out set, unless the `motion4` stall counts.
- **Short clean data.** 0.449 h is too little to support any FA/h claim below about 8/h.
- **No physical actuation.** Nothing in HELIX commands the robot, and no recovery was attempted or claimed. "Verified stop" means the sensors agree that motion ended. It does not mean HELIX made the robot stop.
- **One robot, one firmware.** All recordings come from one GO2. The thresholds are DEV-calibrated for it.
